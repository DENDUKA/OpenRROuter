# Code Review: AuthService

## Результаты ревью

Изучены все файлы AuthService (38 .cs файлов) и все тесты (17 файлов).

---

## Критические проблемы

### 1. Raw API ключи хранятся в БД
**Файл:** `src/OpenRussiaRouter.AuthService/Domain/Entities/ApiKey.cs:29`, `Infrastructure/Repository/AuthRepository.cs:157`

`ApiKey.RawKey` (`string?`) сохраняется в колонке `raw_key` таблицы `auth.api_keys`. Если БД скомпрометирована — все API ключи в открытом виде. Raw key должен возвращаться только при создании и не храниться.

**Рекомендация:** Убрать колонку `raw_key` из схемы. При bulk-sync (`ListAllActiveApiKeysRawAsync`) использовать替代 подход (например, хранить зашифрованную версию или передавать ключи иным способом).

---

### 2. Неверный error code при невалидном email
**Файл:** `src/OpenRussiaRouter.AuthService/Application/Services/AuthAccountApplicationService.cs:59-62`

```csharp
catch (ArgumentException)
{
    return RegisterResult.Failed(AuthErrorCodes.EmailAlreadyRegistered); // ← неверно
}
```

Если `EmailValidator.Normalize` бросает `ArgumentException` (невалидный формат email), возвращается `EmailAlreadyRegistered` вместо `InvalidEmail`. Это сбивает клиента — он решает, что email уже зарегистрирован.

**Рекомендация:** Добавить `AuthErrorCodes.InvalidEmail = "invalid_email"` и использовать его.

---

### 3. GoogleAuthService не принимает nowUtc
**Файл:** `src/OpenRussiaRouter.AuthService/Application/Services/GoogleAuthService.cs:61`

```csharp
var nowUtc = DateTimeOffset.UtcNow; // ← захардкожено
```

Все остальные методы в сервисе принимают `nowUtc` как параметр. Это делает GoogleAuthService не тестируемым для time-dependent сценариев и нарушает единообразие.

**Рекомендация:** Добавить параметр `DateTimeOffset nowUtc` в `LoginOrRegisterWithGoogleAsync`.

---

### 4. InMemoryAuthRepository: AddUserAndMarkInviteUsedAsync не помечает инвайт
**Файл:** `src/OpenRussiaRouter.AuthService/Infrastructure/Repository/InMemoryAuthRepository.cs:29-33`

Dapper-версия проверяет `invite.UsedAtUtc.HasValue` и бросает исключение. In-memory версия просто добавляет пользователя без какой-либо валидации состояния инвайта. Это behavioral inconsistency между двумя реализациями.

**Рекомендация:** Добавить `invite.MarkUsed(nowUtc)` в in-memory реализацию.

## Высокий приоритет

### 5. RenameApiKey: behavioral inconsistency между Dapper и InMemory
**Файл:** `src/OpenRussiaRouter.AuthService/Infrastructure/Repository/AuthRepository.cs:213` vs `InMemoryAuthRepository.cs:129`

Dapper SQL: `disabled_at_utc is null` — разрешает переименование только активных ключей.
InMemory: `SingleOrDefault(k => k.UserId == userId && k.Id == apiKeyId)` — позволяет переименовывать отключённые ключи.

**Рекомендация:** Привести к единому поведению (Dapper-вариант строже — верный).

---

### 6. SQL конкатенация в ListUsersAsync / ListApiKeysAsync
**Файл:** `src/OpenRussiaRouter.AuthService/Infrastructure/Repository/AuthRepository.cs:106-111, 183-193`

```csharp
var afterCondition = "";
if (afterUserId != null)
{
    afterCondition = " where id > @AfterUserId "; // ← string concat
    parameters.Add("AfterUserId", afterUserId);
}
```

Паттерн хрупкий. Хотя `afterUserId` сейчас приходит из внутреннего кода, если когда-нибудь попадёт от пользователя — будет SQL injection.

**Рекомендация:** Использовать parameterized conditional в Dapper или `SqlBuilder`.

### 7. GrpcAuthService: CreateApiKey ловит Exception вместо Specific
**Файл:** `src/OpenRussiaRouter.AuthService/Infrastructure/Grpc/GrpcAuthService.cs:231`

```csharp
catch (Exception ex) when (ex is ArgumentException or InvalidOperationException)
```

Но `AuthAccountApplicationService.CreateApiKeyAsync` больше не бросает исключения — он возвращает `CreateApiKeyResult.Failed()`. Catch блок мёртвый код для этого сценария (хотя может ловить ошибки от `Preconditions.RequireValue`).

**Рекомендация:** Убрать try/catch или сузить до реальных исключений.

## Средний приоритет

### 9. Сессии не персистятся
`LoginService.IssueSession` создает `UserSession` в памяти. При рестарте сервера все сессии аннулируются. Это может быть intentional, но должно быть задокументировано.

### 10. DefaultPageSize = 1000 без пагинации для клиентов
`ListApiKeysAsync` и `ListUsersAsync` в `AuthAccountApplicationService` жёстко лимитируют до 1000 записей без возможности запросить следующую страницу.

### 11. Dual lookup в InMemoryAuthApiKeyValidator
Валидатор сначала проверяет `_repository`, потом `_keysByHash`. Если ключ есть в обоих — приоритет у репозитория. Это может запутать при отладке.

### 12. MarkApiKeyUsedAsync в DapperAuthApiKeyValidator вызывается без проверки IsActive
`DapperAuthApiKeyValidator.ValidateAsync` (строка 22) вызывает `MarkApiKeyUsedAsync` сразу после `FindActiveApiKeyBySecretHashAsync`, но `FindActiveApiKeyBySecretHashAsync` уже фильтрует по `disabled_at_utc is null`. Нет реальной проблемы, но проверка избыточна.

## Низкий приоритет / Качество кода

### 13. GrpcAuthService — 454 строк
Файл-монолит. Можно разделить на отдельные gRPC-сервисы (Invite, ApiKey, User, Session).

### 14. Дублирование тестового кода
`TestAuthRepository` в `AuthAccountApplicationServiceTests` — копия `InMemoryAuthRepository` без `lock`. Множество тестовых файлов создают сервисы с одинаковым boilerplate.

### 15. EmailVerification не имеет Id
Таблица `email_verifications` идентифицируется по `user_id` — нет первичного ключа `id`. ОК для текущего use case, но не расширяемо.

### 16. Нет валидации формата displayCurrency
`UserAccount.UpdateDetails` принимает любой `string` для `displayCurrency`. Нет проверки на ISO 4217.

### 17. MarkApiKeyUsedAsync throttling без документации
`AuthRepository.cs:314` — обновляет `last_used_at_utc` только если прошло > 1 минуты. Хорошая оптимизация, но undocumented.

## Что сделано хорошо

- Чистая слойчатая архитектура: Domain → Application → Infrastructure
- Domain entities инкапсулируют инварианты (ApiKey.Delete требует Disable, Invite.MarkUsed проверяет IsUsed)
- SHA-256 для хеша ключей + PBKDF2 для паролей (210K итераций) — хорошая криптографическая база
- Fixed-time comparison через `CryptographicOperations.FixedTimeEquals` — защита от timing attacks
- `EmailVerificationService` — корректная логика с TTL, cooldown, max attempts
- Транзакционные операции в Dapper-репозитории (AddUserAndMarkInviteUsedAsync, ActivateUserAndDeleteVerificationAsync)
- `MarkApiKeyUsedAsync` throttle для предотвращения частых обновлений
- Тесты покрывают happy path и edge cases (lockout, expiry, cooldown, disabled user)
