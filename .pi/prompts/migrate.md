# Новая миграция в `db/migrations/$1`

`$1` — область: `auth | billing | control | gateway | analytics | content`.
Если `$1` не из списка — **остановись**, не угадывай папку.

## 1. Следующий числовый префикс

```bash
ls "db/migrations/$1"/*.sql | sed -E 's|.*/([0-9]+)_.*\.sql|\1|' | sort -n | tail -1
```

Новый файл: `db/migrations/$1/{NNN}_{slug}.sql`, где `NNN` = `(max+1)` с ведущими нулями до 3 цифр
(напр. `024_add_user_locale.sql`).

Если файл с таким именем уже существует — **не перезаписывай**, возьми следующий префикс.

## 2. Инварианты (не нарушать)

- **Иммутабельность**: применённую миграцию НЕ редактировать. Нужно поменять схему → добавляй
  новый файл со следующим префиксом. (Источник: корневой `CLAUDE.md`, «SQL-миграции».)
- Чистый SQL, применяется `PostgresSqlMigrationRunner` на старте сервиса. Никаких EF-миграций.
- Идемпотентность желательна (`IF NOT EXISTS` / `CREATE OR REPLACE`), но не обязательна —
  раннер ведёт таблицу применённых.

## 3. Шаблон

```sql
-- $1 / {NNN}_{slug}.sql
-- Цель: <одной строкой>

BEGIN;
-- DDL здесь
COMMIT;
```

## 4. Отчёт (observation-контракт)

- **status**: `created`
- **summary**: что меняет миграция (одной строкой)
- **artifacts**: путь к новому файлу
- **next_actions**: «применится автоматически при следующем старте сервиса; локально — через
  Testcontainers/локальную PG. Для прогона: `/build-test <Service>`»

## Error recovery

- **root cause**: если два файла получили одинаковый префикс — кто применён первым выигрывает,
  второй надо переименовать.
- **safe retry**: переименуй конфликтующий файл в следующий свободный префикс.
- **stop condition**: не правь уже применённую миграцию — заворачивай изменение в новую.
