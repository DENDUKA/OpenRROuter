# Безопасная интеграция PostHog

## Постановка задачи

В OpenRussiaRouter уже добавлена базовая клиентская интеграция PostHog: JavaScript SDK загружается в общем layout, собирает браузерные события и связывает их с авторизованным пользователем. Текущий вариант недостаточно безопасен для production, поскольку browser SDK потенциально может получить доступ к содержимому страниц с API-ключами, control tokens, пользовательскими данными и параметрами URL. Кроме того, development, staging и production не разделены, а значимые продуктовые действия пока не фиксируются серверными событиями.

Необходимо заменить существующее подключение на privacy-first интеграцию PostHog, которая позволит измерять активацию, использование API, удержание пользователей и конверсию в оплату, не передавая в систему аналитики пользовательские секреты, содержимое LLM-запросов и прямые персональные идентификаторы.

В рамках задачи требуется:

1. Остановить и удалить текущий клиентский сбор PostHog из WebApp.
2. Проверить, не могли ли session recordings содержать API keys или control tokens, и определить порядок реагирования при обнаружении таких записей.
3. Ввести серверную абстракцию продуктовой аналитики с отключаемой `NoOp`-реализацией.
4. Подключить PostHog через официальный серверный .NET SDK.
5. Псевдонимизировать пользователей при помощи стабильного HMAC-идентификатора.
6. Определить закрытый перечень событий и разрешённых свойств.
7. Отправлять события только после успешного завершения соответствующих бизнес-операций.
8. Исключить передачу email, имён, внутренних идентификаторов, API keys, control tokens, prompt/response, платёжных идентификаторов и сырых payload.
9. Разделить development, tests, staging и production.
10. Обеспечить безопасное отключение аналитики, удаление пользовательских данных, тестирование и контролируемый rollout.
11. Сохранить возможность выбора между PostHog Cloud и размещением PostHog на инфраструктуре в РФ.

Ожидаемый результат — отказоустойчивая серверная интеграция, которая предоставляет продуктовые воронки и метрики без присутствия PostHog в браузере и без влияния аналитики на регистрацию, API-запросы, billing и платежи.

В задачу первой итерации не входят:

- session replay;
- browser autocapture;
- heatmaps;
- сбор произвольных UI-кликов;
- передача prompt и response в AI Observability;
- использование PostHog как замены Prometheus, Grafana или Seq;
- feature flags и эксперименты.

## Целевая схема

Наиболее консервативный вариант — полностью убрать PostHog из браузера и отправлять только серверные события по строгому контракту.

```text
Пользователь → ORR WebApp/API
                    │
                    ▼
           IProductAnalytics
                    │
       фильтрация + псевдонимизация
                    │
                    ▼
        PostHog Cloud / PostHog в РФ
```

Такая схема исключает session replay, сторонние cookies, autocapture, попадание содержимого страниц и секретов, передачу prompt/response и прямую передачу клиентского IP в PostHog.

## 1. Немедленно остановить текущий клиентский сбор

> **Что утекает прямо сейчас.** Текущий snippet (`Pages/Shared/_Layout.cshtml`) для каждого авторизованного пользователя вызывает `posthog.identify(UserId, { email, name })` и отправляет данные на **US Cloud** (`https://us.i.posthog.com`) — не EU и не РФ. Помимо этого по умолчанию активны autocapture и `$pageview` с `$current_url` (включая query-параметры путей `/workspace/apikeys`, `/admin/*`). Session Replay в posthog-js по умолчанию **выключен** (включается на стороне проекта), поэтому основной канал утечки — это `identify` + autocapture + pageviews, а не записи страниц. Это уже состоявшаяся трансграничная передача ПДн (email, имя, сырой `UserId`) в США.

Порядок реагирования:

1. Удалить текущий PostHog snippet целиком из `src/OpenRussiaRouter.WebApp/Pages/Shared/_Layout.cshtml` вместе с чтениями `Configuration["PostHog:*"]`.
2. Удалить всю секцию `PostHog` (а не только token) из базового `src/OpenRussiaRouter.WebApp/appsettings.json` и из остальных конфигов/overlay.
3. В настройках проекта PostHog выключить Session Replay (на случай, если включался).
4. Удалить **person-профили** проекта — именно в них хранятся email, имя и сырой `UserId`. Удаления одних только session recordings недостаточно.
5. Вычистить накопленные `$pageview`/autocapture-события за период работы snippet, обращая внимание на свойства `$current_url`/`$pathname`, где могли оказаться токены в query string.
6. Проверить, создавались ли записи страниц `/workspace/apikeys`, `/admin/nodes`, `/admin/node-details`, `/admin/gateway-test`; при наличии — удалить.
7. Если в записях или событиях могли отобразиться секреты — сменить показанные API keys и control tokens.
8. **Перевыпустить project API key** проекта PostHog. Текущий `phc_*`-токен закоммичен в `appsettings.json` и попал в историю git; хотя это write-only ключ (не «секрет»), любой с ним может продолжать слать события в проект — перевыпуск дешевле, чем оставлять неопределённость.

Критерий завершения: браузер не загружает `array.js`, не обращается к `*.posthog.com` и не создаёт `ph_*` cookies или записи в local storage; в проекте PostHog отсутствуют person-профили со старыми email/именами.

## 2. Выбрать место хранения

На уровне конфигурации необходимо поддержать два назначения:

- предпочтительно для максимальной юридической консервативности — self-hosted PostHog на инфраструктуре в РФ;
- PostHog Cloud — только после юридической проверки, обновления политики конфиденциальности и выполнения требований по трансграничной передаче данных.

EU Cloud остаётся зарубежной базой и сам по себе вопрос соблюдения требований 152-ФЗ не закрывает.

> **Сначала решить, нужен ли вообще серверный PostHog.** Self-hosted PostHog — это полный тяжёлый стек (ClickHouse, Kafka, Redis, Postgres, MinIO), нетривиальный в эксплуатации, патчинге и безопасности, с урезанной поддержкой self-host. Цель первой итерации — всего четыре события и несколько воронок, а у ORR уже есть Prometheus/Grafana/Seq. Прежде чем поднимать PostHog, сопоставьте его с альтернативой «хранить эти события в собственном Postgres + дашборды в Grafana», которая закрывает 152-ФЗ без отдельной аналитической платформы. Решение принимается на этом шаге, до коммита в PostHog.

До принятия решения аналитика должна оставаться выключенной:

```json
{
  "ProductAnalytics": {
    "Enabled": false,
    "Provider": "PostHog",
    "HostUrl": "",
    "ProjectToken": "",
    "IdentitySalt": "",
    "Environment": "production"
  }
}
```

## 3. Разделить окружения

Следует создать отдельные конфигурации:

- development — аналитика выключена;
- tests/E2E — используется `NoOpProductAnalytics`;
- staging — отдельный проект PostHog;
- production — отдельный проект и отдельный `IdentitySalt`.

В production значения передаются через environment variables или secret store:

```text
ProductAnalytics__Enabled
ProductAnalytics__HostUrl
ProductAnalytics__ProjectToken
ProductAnalytics__IdentitySalt
ProductAnalytics__Environment
```

`ProjectToken` не является секретом, но `IdentitySalt` является. Salt нельзя коммитить или регулярно менять: после его смены существующие пользователи будут представлены в аналитике как новые.

## 4. Ввести серверную абстракцию

В `OpenRussiaRouter.BuildingBlocks` следует добавить контракт:

```csharp
public interface IProductAnalytics
{
    void UserVerified(string userId, string signupMethod);
    void ApiKeyCreated(string userId);
    void ApiRequestCompleted(string userId, ApiRequestAnalytics data);
    void PaymentCompleted(string userId, PaymentAnalytics data);
}
```

Необходимы две реализации:

- `NoOpProductAnalytics`;
- `PostHogProductAnalytics`.

Правило выбора реализации в DI: при `Enabled=false` **или** пустом `ProjectToken` биндится `NoOpProductAnalytics`; `PostHogProductAnalytics` регистрируется только когда аналитика включена и сконфигурирована.

Использование `IPostHogClient.Capture()` напрямую из бизнес-кода необходимо запретить. Сервисы должны работать только через типизированные методы. Это уменьшает вероятность случайной отправки email, prompt, API key или произвольного payload. Запрет нужно **enforce-ить механически**, а не только на ревью: Roslyn-анализатор или grep-тест в CI, проверяющий, что `Capture(` не встречается вне `PostHogProductAnalytics`.

Методы контракта синхронные (`void`) и лишь ставят событие во внутреннюю очередь; фактическая отправка асинхронна (см. раздел 7). Поэтому enqueue обязан быть обёрнут catch-all, а на переполнении очереди — **drop без throw и без блокировки**, чтобы аналитика не могла повлиять на бизнес-путь.

Пакет `PostHog.AspNetCore` следует подключить через централизованное управление версиями в `Directory.Packages.props`. SDK относительно новый — зафиксировать версию и проверить, что она поддерживает явное задание `uuid` события (нужно для дедупа, раздел 7) и отключение geoip.

## 5. Псевдонимизировать пользователя

Внутренний `UserId` нельзя отправлять напрямую.

```text
distinct_id = Base64Url(
    HMAC-SHA256(IdentitySalt, UserId)
)
```

В PostHog нельзя передавать:

- email и имя;
- исходный `UserId`;
- session token;
- API key ID, prefix или raw key;
- клиентский IP и user-agent;
- payment ID, order ID и provider payment ID.

При удалении аккаунта тот же HMAC позволяет вычислить соответствующий `distinct_id` и удалить данные пользователя из PostHog.

> **Псевдонимизация ≠ обезличивание.** Keyed-HMAC от `UserId` под 152-ФЗ/GDPR остаётся персональными данными: контроллер может реидентифицировать пользователя, имея salt. Это снижает экспозицию, но **не выводит данные из-под прав субъекта и трансграничных требований** — в юридической проверке (разделы 2 и 11) нельзя подавать эти данные как «обезличенные». Стойкость зависит от пространства `UserId`: для GUID keyed-HMAC надёжен; для последовательного int при утечке salt он брутфорсится. Зафиксировать, что `UserId` — неугадываемый идентификатор.
>
> **Клиентский IP при серверной отправке не утекает «по умолчанию».** События уходят с сервера, и PostHog видит egress-IP сервера, а не пользователя — это плюс серверной схемы. Нужно лишь убедиться, что `$ip` не проставляется форварднутым клиентским IP, и при желании выставить `$geoip_disable`.

## 6. Зафиксировать контракт событий

### `user verified`

Разрешённые свойства:

- `signup_method`: `email` или `google`;
- `schema_version`;
- `environment`.

### `api key created`

Событие не должно содержать имя, ID, prefix или значение ключа.

Разрешённые свойства:

- `schema_version`;
- `environment`.

### `api request completed`

Разрешённые свойства:

- `endpoint`: `chat_completions` или `tts`;
- `model`;
- `stream`;
- `status_class`;
- `input_tokens_bucket`;
- `output_tokens_bucket`;
- `latency_bucket`;
- `schema_version`;
- `environment`.

### `payment completed`

Разрешённые свойства:

- `provider`;
- `currency`;
- `amount_bucket`;
- `schema_version`;
- `environment`.

На первом этапе безопаснее использовать диапазоны значений, например `1-1K` и `1K-10K`, вместо точных сумм и количества токенов.

### Запрещённые свойства

```text
email
name
prompt
response
content
message
token
secret
api_key
control_token
raw_payload
authorization
cookie
```

Первичный механизм — **закрытый allow-list свойств на каждое событие (default-deny)**: любое свойство, не входящее в перечень разрешённых для данного события, отбрасывается. Перечисленный выше список запрещённых ключей — это defense-in-depth/бэкап, а не основная защита (deny-list в одиночку хрупок: забыли ключ — утечка). Оба механизма должны проверяться тестами и защитным фильтром непосредственно перед отправкой события.

## 7. Подключить события в авторитетных сервисах

Событие отправляется в сервисе, который окончательно подтверждает завершение операции:

- `user verified` — после успешного `VerifyEmailAsync()` в `AuthAccountApplicationService`;
- `api key created` — после сохранения ключа в `AuthAccountApplicationService`, а не в WebApp;
- `api request completed` — после успешного и идемпотентного `RecordUsageAsync()` в `BillingApplicationService`;
- `payment completed` — после атомарного подтверждения платежа в `BillingService`.

Аналитика должна быть fail-open:

- ошибка PostHog никогда не ломает регистрацию, API-запрос или платёж;
- отправка выполняется асинхронно;
- внутренняя очередь ограничена;
- в технический лог записывается только имя события без properties.

Дедуп повторных webhook/usage-сообщений нужно привязать к **`uuid` события PostHog** (`$insert_id`): задавать его детерминированным GUID, производным от бизнес-идентификатора (`usage_record_id`, `payment_id`). «Детерминированный идентификатор» сам по себе не дедуплицирует — PostHog схлопывает дубли именно по `uuid` события. Без явного `uuid` повторная доставка создаст второе `payment completed`.

Следствие асинхронности: на аварийном завершении или быстром SIGTERM пода буфер SDK может потеряться — гарантия доставки **at-most-once**. Для аналитики это приемлемо (события не billing), но это нужно держать в голове: `payment completed` в аналитике не является источником истины.

Поскольку эмиссия переезжает в backend-сервисы (Auth/Billing), а не в WebApp, проверить, что k8s network policy этих подов разрешает egress на хост PostHog (наружу сейчас ходит WebApp).

## 8. Не подключать browser SDK на первом этапе

Первая версия будет измерять:

- активацию;
- retention;
- использование API;
- конверсию в оплату.

Она осознанно не будет собирать клики и просмотры публичных страниц.

Если позднее понадобятся UI-события, следует добавить собственный endpoint:

```text
POST /internal/analytics/events
```

Endpoint должен:

- требовать авторизацию и antiforgery token;
- принимать только enum события;
- не принимать произвольный словарь properties;
- вычислять `distinct_id` на сервере;
- иметь rate limit;
- отправлять событие через `IProductAnalytics`.

PostHog JavaScript SDK для такой схемы не требуется.

## 9. Реализовать удаление данных

Процесс удаления аккаунта должен:

1. вычислить PostHog `distinct_id` через HMAC;
2. поставить удаление аналитических данных в служебную очередь;
3. удалить или обезличить профиль и связанные события в соответствии с возможностями выбранного размещения PostHog;
4. зафиксировать только результат операции, не сохраняя аналитический идентификатор в открытом виде дольше необходимого.

Если для API удаления требуется PostHog Personal API Key, он хранится только в production secret store и никогда не передаётся браузеру.

Два ограничения, которые нужно учесть:

- удаление person/событий в PostHog **асинхронно** (ClickHouse, батч-удаление), а на Cloud зависит от их GDPR-процесса — «удаление при удалении аккаунта» не мгновенно; зафиксировать ожидаемый SLA и то, что подтверждение приходит позже постановки в очередь;
- вычисление `distinct_id` для удаления требует `IdentitySalt` на момент удаления. Потеря salt делает точечное удаление невозможным навсегда — salt должен входить в ту же надёжную backup-/recovery-историю, что и остальные production-секреты.

## 10. Тестирование

Обязательные проверки:

- unit-тест HMAC: результат стабилен и не содержит исходный `UserId`;
- contract-тест: запрещённые свойства невозможно передать;
- integration-тест через fake HTTP handler: payload не содержит email, prompt, token и secret;
- E2E-тест: браузер не обращается к доменам PostHog;
- E2E-тест: отсутствуют PostHog cookies и записи в local storage;
- события не отправляются при `Enabled=false`;
- сбой PostHog не влияет на ответ API и обработку платежа;
- повторный webhook не создаёт два события `payment completed`;
- development и E2E не отправляют события в production-проект;
- contract-тест: защитный фильтр срезает **намеренно вставленное** запрещённое свойство (не только «типизированный API не даёт его добавить» — поля DTO вроде `ApiRequestAnalytics` со временем расширят);
- каждое событие содержит `schema_version`;
- CI-guard: `IPostHogClient.Capture(` не встречается вне `PostHogProductAnalytics`;
- два события с одинаковым бизнес-идентификатором получают одинаковый `uuid` (дедуп).

## 11. Безопасный rollout

1. Развернуть реализацию с `Enabled=false`.
2. Проверить отсутствие клиентского PostHog.
3. Включить staging и проверить фактический payload в тестовом проекте.
4. Удалить тестовые данные.
5. Провести юридическую проверку выбранного размещения.
6. Включить production.
7. Создать dashboards:
   - `user verified → api key created → first api request`;
   - weekly users with successful API requests;
   - `first api request → payment completed`;
   - использование по моделям и endpoint.
8. Установить минимально необходимый retention.
9. Включить MFA и минимальные роли доступа в PostHog.
10. Настроить лимит расходов.
11. Раз в месяц проверять новые события и свойства.

Аварийное отключение должно выполняться одной настройкой:

```text
ProductAnalytics__Enabled=false
```

Этот переключатель действует через DI-свап на `NoOpProductAnalytics` и применяется **после рестарта** сервиса. Если требуется мгновенное отключение без редеплоя, `PostHogProductAnalytics` должен дополнительно проверять (кешированный) флаг на каждый вызов. Зафиксировать, какой вариант принят.

## Критерии готовности

Интеграция считается готовой, когда:

- в браузере отсутствует PostHog SDK;
- никакие пользовательские секреты и содержимое LLM-запросов не покидают ORR;
- все пользователи представлены только HMAC-идентификаторами;
- разрешённые события и свойства описаны типизированными контрактами;
- аналитика не влияет на основной бизнес-процесс при сбое;
- development, staging и production полностью разделены;
- реализованы отключение аналитики и удаление пользовательских данных;
- выбранное место хранения прошло юридическую проверку.
