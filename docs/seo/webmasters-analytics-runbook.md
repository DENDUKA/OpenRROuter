# Runbook: подключение вебмастеров и аналитики (SEO-002)

Подключение `rawrter.com` к Google Search Console, Яндекс Вебмастеру, Яндекс Метрике
и Google Analytics 4. Итоговый критерий: домен подтверждён в обеих системах, счётчики отдают
события конверсии (регистрация → подтверждение email → создание API-ключа → первое пополнение).

## Разделение ответственности

| Шаг | Кто |
|---|---|
| DNS-подтверждение, аккаунты, счётчики, связки, цели | человек (владелец аккаунтов) |
| Вставка тегов в layout, CSP-хосты, конверсионные события, тесты | агент (код) |

## 0. Предусловия

- Прод задеплоен, `https://rawrter.com` отвечает, `/robots.txt` и `/sitemap.xml` отдают 200.
- Доступ к DNS-панели `rawrter.com`.
- Аккаунты Google (Search Console + GA4) и Яндекс (Вебмастер + Метрика).

## 1. Google Search Console (руками)

1. Search Console → «Добавить ресурс» → тип **«Домен»** (`rawrter.com`).
2. Способ подтверждения → **DNS-запись**, скопировать `google-site-verification=...`.
3. Добавить эту **TXT-запись** в DNS (пропагация обычно ≤ 1ч).
4. Подтвердить в консоли.

## 2. Яндекс Вебмастер (руками)

1. Добавить сайт `rawrter.com` → «Подтверждение прав».
2. Способ → **DNS-запись**: TXT `yandex-verification: <hex>`.
3. Добавить в DNS, подтвердить.

## 3. Google Analytics 4 (руками)

1. Создать GA4-свойство → Web data stream на `https://rawrter.com`.
2. Получить **Measurement ID** `G-XXXXXXX`.
3. (опционально) Enhanced Measurement.

## 4. Яндекс Метрика (руками)

1. Создать счётчик (тип «Сайт»), домен `rawrter.com`.
2. Получить **номер счётчика**.
3. В настройках: включить **анонимизацию IP**; Webvisor — на усмотрение (пишет видео-сессии,
   конфликтует с privacy-позой сервиса «визиты без кук и raw IP», в коде включён
   `webvisor:true` в init — при необходимости выключить).

## 5. Связка GSC ↔ GA4 (руками)

GA4 → Admin → Property → **Search Console links** → добавить GSC-ресурс.

## 6. Внедрение кода (агент)

- `AnalyticsOptions` (`GoogleTagId`, `YandexCounterId`), секция `Analytics` в `appsettings.json`.
- `_Layout.cshtml`: gtag.js + счётчик Метрики в `<head>`, gated по непустым ID;
  конверсии через `ViewData["AnalyticsEvents"]`.
- `Program.cs`: CSP расширяется **условно** — при `GoogleTagId` в `connect-src` добавляются
  `googletagmanager.com`, **wildcard `*.google-analytics.com`** (покрывает `www` и региональные
  collect-endpoint'ы GA4 `region1..N.google-analytics.com` — gtag.js выбирает `regionN` по
  настройкам свойства/consent, а не по IP посетителя) и **голый `analytics.google.com`**
  отдельным источником (CSP-wildcard матчит поддомены, но не родительский домен);
  в `script-src` — `googletagmanager.com`, в `img-src` — `www.google-analytics.com`.
  При `YandexCounterId` — `mc.yandex.ru`, `mc.yandex.com` (cookie-sync пиксель +
  `wss://mc.yandex.com/solid.ws`), `mc.webvisor.org`/`mc.webvisor.com`, `yastatic.net`;
  `wss:`-схема в `connect-src` перечисляется отдельно от `https:` — браузер не считает
  `https://host` покрывающим `wss://host`.
- Прод-значения — в `deploy/compose/compose.prod.yml` (`Analytics__GoogleTagId`,
  `Analytics__YandexCounterId`).
- **`/docs` — отдельный контейнер VitePress, layout WebApp туда не доезжает.** GA4 подключён
  собственным `head` в `docs-site/.vitepress/config.mts` тем же measurement id (общий поток —
  иначе переход сайт → документация рвёт сессию). Consent Mode ставится до `gtag.js` по cookie
  `orr_consent`; своего баннера у документации нет. Правка конфига доезжает до прода **только
  пересборкой контейнера `docs`**. Счётчика Метрики в документации пока нет.
- Тесты в `SeoHeadTests`: без конфига тегов нет; с конфигом — оба сниппета на месте.

### Конверсионные события

**Источник истины имён — [`Services/Analytics/AnalyticsGoals.cs`](../../src/OpenRussiaRouter.WebApp/Services/Analytics/AnalyticsGoals.cs)**,
таблицы ниже — производное зеркало. Правится реестр, не документ.

#### Макро — воронка (только эти помечаются конверсиями)

| Цель | Событие | Где | Механизм |
|---|---|---|---|
| Регистрация | `signup` | `/verify-email` после signup, либо `/workspace/apikeys` после OAuth-регистрации | `AnalyticsTempData` |
| Подтверждение email | `email_verified` | `/workspace/apikeys` после верификации либо после OAuth-регистрации | `AnalyticsTempData` |
| Создание API-ключа (**активация**) | `api_key_created` | `/workspace/apikeys` после создания | `AnalyticsTempData` |
| Пополнение | `topup_completed` | `/workspace/credits` после возврата от провайдера | `AnalyticsTempData`, **с ценностью** |

**OAuth-регистрация закрывает оба первых шага одним рендером.** У Google/Яндекс нет отдельного
шага подтверждения почты — провайдер уже подтвердил владение, поэтому
`ExternalCallback` кладёт `signup` + `email_verified` вместе. Без этого каждая регистрация через
внешний провайдер была невидима: цели ставились только на пути через `/verify-email`.
Признак «аккаунт создан именно этим вызовом» приезжает в `LoginResponse.is_new_user` (`auth.proto`);
линковка провайдера к уже существующему аккаунту новой регистрацией **не считается**.

«Первое» пополнение в GA4/Метрике считается по distinct user в отчётах — клиент не знает «первое ли».

#### Микро — интерес и намерение (конверсиями **не** помечать)

Вешаются декларативно, атрибутом `data-goal="<имя>"` на элемент; делегированный обработчик
в `_Layout.cshtml` ловит клик и шлёт цель. Новая микро-цель = константа в `AnalyticsGoals` +
атрибут в разметке, кода не пишется.

| Цель | Где |
|---|---|
| `cta_signup_hero`, `cta_signup_quickstart`, `cta_signup_final` | три CTA регистрации на лендинге (разведены по позиции — они на одной странице) |
| `cta_models_hero`, `cta_models_catalog`, `cta_models_final` | три CTA «Каталог моделей» там же |
| `cta_apikey_model`, `cta_apikey_provider` | «Получить API-ключ» с карточки модели и провайдера |
| `copy_model_id` | копирование id модели в `/models` |
| `copy_code_sample` | копирование примера интеграции (`_IntegrationExamples`) |
| `copy_base_url` | копирование базового URL на `/docs` |
| `copy_api_key` | копирование только что созданного ключа |
| `cta_oauth_google`, `cta_oauth_yandex` | кнопки внешнего входа (одно имя на `/login` и `/signup` — цели и так режутся по URL достижения) |
| `checkout_started` | сабмит формы пополнения и кнопка Yandex Pay; фиксирует намерение даже если Billing отклонил чекаут |
| `support_submitted` | успешная отправка формы поддержки (серверная цель: клик по кнопке случается и при провале валидации, и на ханипоте) |

## 7. Настройка целей (руками, после деплоя)

Код уже шлёт события в оба счётчика автоматически (`gtag('event', …)` + `ym(…,'reachGoal',…)`),
в кабинетах их нужно только **объявить целями/конверсиями**. События придут после деплоя кода —
до этого теги не активны, настройка целей впрок бессмысленна.

### 7.1 Google Analytics 4 — пометить события как conversions

1. GA4 → **Admin** → колонка Property → **Conversions**.
2. **New conversion event** → **только четыре макро-имени**: `signup`, `email_verified`,
   `api_key_created`, `topup_completed`.
3. Сохранить. Появятся в отчётах Conversions и в главном табло «Конверсии».

**Микро-цели конверсиями не помечать.** Их на порядок больше, они срабатывают у каждого второго
посетителя, и в conversions они превратят собственный «коэффициент конверсии» GA4 в шум. Место
микро-целей — Explorations и сегменты.

Опционально:
- **Admin → Property → Events**: события появятся сами после первого попадания данных
  (проверить, что имя точное — регистр важен).
- **Explorations / Reports**: строить воронку `signup → email_verified → api_key_created →
  topup_completed` по событиям.
- Связка с Search Console — шаг 5.

### 7.2 Яндекс Метрика — объявить цели

`ym(111582266, 'reachGoal', …)` отправляет события через «Достижение целей». Метрика сама
заведёт события по факту прихода, но цель нужно объявить явно, иначе её нет в отчётах:

1. Счётчик → раздел **«Цели»** в левом меню (прямой адрес — `/settings?id=<counter>&tab=goals`;
   пункт меню «Цели» ведёт в **отчёт**, а не в настройки, а `/settings/goals` отдаёт 404).
2. **Добавить цель** → тип **«Целевое событие • ex JS-событие»** — он один на все цели,
   и макро, и микро.
3. **Название цели** — человекочитаемое, **Идентификатор цели** — имя из `AnalyticsGoals`.
   Регистр важен, имена только в нижнем snake_case.
4. **Условие обязательно переключить с «Содержит» на «Совпадает».** ⚠️ «Содержит» —
   значение по умолчанию, и на нашем наборе имён оно тихо ломает воронку: `cta_signup_hero`,
   `cta_signup_quickstart` и `cta_signup_final` каждое **содержит** подстроку `signup`, поэтому
   макро-цель «Регистрация» начнёт засчитываться по кликам людей, которые не регистрировались.
   Симптом — не ошибка, а завышенные в разы регистрации. Проверять по списку: у правильной
   цели написано «идентификатор: X», у сломанной — «идентификатор **содержит**: X».
5. Сохранить. Каждый `reachGoal(...)` станет достижением цели.

**Отдельной галки «Цель с ценностью» в текущем интерфейсе нет.** В форме есть только
«Дополнительные настройки → Статический доход» — это фиксированная сумма на каждое достижение,
нам она не нужна и включать её не надо: `topup_completed` передаёт реальную сумму динамически
(`order_price` + `currency` четвёртым аргументом `reachGoal`). Что динамическая ценность
доезжает, проверяется только сквозной тест-конверсией — см. §8.

Проверка: Метрика → **Realtime** → «Цели» — должны появляться после тестовых действий;
отчёт «Конверсии» покажет воронку и, для пополнения, сумму.

### 7.3 Что учесть

- **«Первое пополнение»** (`topup_completed`) — в обоих системах это просто «пополнение»;
  «первое» выводится сегментацией по пользователю в отчётах, а не настройкой цели.
- **Дедупликация макро-целей.** Возврат от провайдера на `/workspace/credits?topup=success`
  отдаёт 302 на чистый URL, а сама цель едет одноразовым `TempData` и потребляется при чтении.
  Обновление страницы (F5) повторную конверсию не даёт ни на одном шаге воронки.
- **Ценность может не доехать.** Сумма переносится от старта чекаута до возврата в cookie
  `TempData`. Если она потерялась (чистка cookie, возврат в другом браузере, admin-only чекаут
  Yandex Pay, который её не ставит), цель всё равно засчитывается — но без `order_price`.
  Занижение выручки предпочтительнее потери конверсии.
- **Микро-цель может потеряться на первых миллисекундах.** Клик по CTA в момент, когда `tag.js`
  ещё не загрузился, не будет отправлен: переход намеренно не задерживается `preventDefault`.
  На макро-воронку это не влияет — все четыре её цели серверные.
- `signup` шлётся только из реальной регистрации (не из логина) — см. `Signup`/`VerifyEmail`
  и ветку OAuth выше.
- **Псевдонимный `setUserID`** уходит только для авторизованных и только после согласия
  на cookie. Ротация `ProductAnalytics:IdentitySalt` рвёт связь с уже накопленными профилями
  в обоих кабинетах.

## 8. Проверка

### 8.1 Серверные offline conversions (`topup_completed`, `first_api_request`)

Rollout выполняется в два этапа, чтобы не потерять и не задвоить пополнения:

1. Создать OAuth-токен Яндекса с правом загрузки офлайн-данных, записать его только в prod `.env`
   как `YANDEX_METRIKA_OAUTH_TOKEN`; сначала оставить `YANDEX_METRIKA_OFFLINE_ENABLED=false`.
2. После деплоя и применения миграций включить worker (`YANDEX_METRIKA_OFFLINE_ENABLED=true`), но
   временно оставить `YANDEX_METRIKA_CLIENT_TOPUP_ENABLED=true`.
3. Новым согласившимся пользователем открыть кабинет, выполнить первый платный API-запрос и
   убедиться, что загрузка `first_api_request` получила статус `PROCESSED`.
4. Установить `YANDEX_METRIKA_CLIENT_TOPUP_ENABLED=false` и выполнить одно реальное тестовое
   пополнение. GA4 продолжает получать `topup_completed`, а Метрика получает его только из outbox.
5. В Метрике оставить точную цель `topup_completed` (ID `597470019`) и точную цель
   `first_api_request`; удалить дублирующие цели лишь после smoke-теста. В отчёте проверить один
   ClientID, одно достижение, сумму провайдера и `RUB`. Обработка Яндексом может занять до трёх часов.

Диагностика начинается с `billing.yandex_metrika_offline_conversion_outbox`: `Pending` без
`resolved_client_id` означает, что браузер ещё не сохранил `_ym_uid`; `Reconciling` — неизвестен
результат предыдущего запроса; `LINKAGE_FAILURE`, mismatch числа строк и постоянные 4xx завершаются
как `Failed`. `401/403` указывают на CounterId/OAuthToken и повторяются с редким интервалом.

- Метрика: «Проверить код», Realtime; GA4: DebugView/Realtime.
- Тест-конверсия на проде: регистрация → верификация → создание ключа → тест-пополнение
  на минимальную сумму; в отчёте «Конверсии» у `topup_completed` должна появиться ненулевая
  ценность в рублях.
- Отчёт «Воронка» на четырёх макро-целях: проверить, что OAuth-когорта не проваливается
  на шаге `email_verified`.
- Sitemap/переобход — задачи SEO-020/SEO-021.

## Юридическая точка — закрыта

Consent-баннер есть (`rwt_consent`, показывается при любом настроенном счётчике), состав cookie
и оба аналитических сервиса описаны в `docs/mandatory/privacy-policy.md` (п. 3.5–3.7), передача
псевдонимного идентификатора — в п. 3.6.1. До согласия вебвизор и карта кликов выключены,
`setUserID` не отправляется.
