# T-007, T-008 и T-018: атомарный лизинг и выбор нод

## Цель

Устранить потерю счётчика `in_flight_requests`, некорректное освобождение протухших лиз и чтение всей таблицы нод на каждом запросе выбора маршрута.

## Решение

Перенести мутабельные операции лизинга в репозиторий PostgreSQL:

- выбор и выдача лизы выполняются транзакционно: SQL выбирает только кандидатов из in-memory снимка метаданных, блокирует строку через `FOR UPDATE SKIP LOCKED`, атомарно увеличивает `in_flight_requests` и создаёт лиз;
- освобождение конкретной и протухших лиз выполняется SQL-операцией с точным количеством лиз на ноду и `greatest(..., 0)`;
- health-путь обновляет только health-колонки, а upsert метаданных не перезаписывает актуальный `in_flight_requests`;
- отдельный воркер обновляет in-memory снимок неизменяемых метаданных нод. Снимок не содержит `in_flight_requests`; текущая нагрузка учитывается только внутри SQL.

In-memory репозиторий сохраняет тот же контракт для unit-тестов и синхронно повторяет атомарную семантику.

## Инварианты

- Отключённая или нездоровая нода не может получить новую лизу даже при устаревшем снимке.
- Capability, preferred-node token и исключённые ноды отфильтровываются до SQL.
- Изменение health/enable/metadata не может обнулить или восстановить счётчик in-flight.
- Удаление N протухших лиз одной ноды уменьшает её счётчик на N в одной операции.
- При пустом capability-store до первого обновления сохраняется существующий least-load fallback.

## Проверка

Добавить unit- и PostgreSQL-интеграционные тесты на параллельную выдачу лиз, точное массовое освобождение, конкуренцию health и лизинга, а также SQL-выбор только из переданных кандидатов. Запустить весь проект тестов ControlPlane и полную сборку solution.

## Вне области

Не менять gRPC-контракт, TTL лизы, правила capability-routing, формат admin API и cooldown health-checker.
