# OR-003: One-shot maintenance для incremental_vacuum 9Router

## Prompt

Добавить явный maintenance-сценарий для существующих SQLite БД 9Router: перевести БД в `auto_vacuum = INCREMENTAL` через full `VACUUM`, только после проверки свободного места и только по явному запуску оператора или opt-in env-флагу.

## Что нужно сделать

### 1. Создать npm-script

В `package.json` добавить:

```json
"db:enable-incremental-vacuum": "node scripts/enable-incremental-vacuum.js"
```

### 2. Реализовать maintenance-скрипт

Скрипт должен:

1. Использовать существующий DB adapter 9Router и уважать `DATA_DIR`.
2. Отказаться работать, если драйвер не `better-sqlite3` / native SQLite. Для `sql.js` вывести понятное сообщение и завершиться без изменения БД.
3. Найти размер `data.sqlite`.
4. Проверить свободное место на том же filesystem.
5. Отказаться запускаться, если `free_space < 2.2 * db_size`.
6. Залогировать план:

```text
[db-maintenance] enabling incremental_vacuum dbSize={...} freeSpace={...}
```

7. Выполнить:

```sql
PRAGMA auto_vacuum = INCREMENTAL;
VACUUM;
```

8. Зафиксировать результат в `_meta`:

- `autoVacuumMode = incremental`
- `autoVacuumMigratedAt = <ISO timestamp>`

9. Залогировать новый размер файла и длительность операции.

Если определить свободное место штатным способом невозможно, скрипт должен завершиться отказом и объяснить, что оператор может запустить вручную только после проверки места. Не делать опасный best-effort full `VACUUM` без проверки.

### 3. Сделать запуск идемпотентным

Если `_meta.autoVacuumMode === "incremental"` и оператор запускает скрипт вручную:

- вывести сообщение `already in incremental mode`;
- показать текущий размер `data.sqlite`;
- завершиться без full `VACUUM`.

Если нужен повторный compaction-запуск, поддержать явный флаг `--force`. Без `--force` повторно перестраивать БД нельзя.

### 4. Проверить, что БД не занята другим процессом

Перед `VACUUM` скрипт должен попытаться быстро получить write lock:

```sql
BEGIN IMMEDIATE;
ROLLBACK;
```

Если lock получить нельзя, завершиться с понятной ошибкой: остановить работающий 9Router-процесс/контейнер и повторить запуск в окно обслуживания.

Это не заменяет проверку свободного места.

### 5. Логировать длительную операцию

Во время `VACUUM` логировать heartbeat, например раз в 10 секунд:

```text
[db-maintenance] VACUUM in progress elapsed={N}s
```

После завершения heartbeat нужно остановить. Если операция длится больше 60 секунд, вывести warning, но не прерывать процесс автоматически.

### 6. Добавить opt-in автозапуск

В `initializeApp.js` добавить поддержку:

```env
ORR_AUTO_RUN_DB_MAINTENANCE=true
```

Если флаг включён:

- запустить maintenance один раз при старте;
- не запускать повторно, если `_meta.autoVacuumMode === "incremental"`;
- ошибки логировать, но не валить приложение.

Если флаг выключен или отсутствует, maintenance не запускается автоматически.

### 7. Обновить runbook

В `docs/9router-vps-deployment-runbook.ru.md` добавить короткую секцию:

- когда запускать `npm run db:enable-incremental-vacuum`;
- как проверить свободное место перед запуском;
- что операция может блокировать запись;
- что на обычных ORR-managed нодах запускать лучше в окно обслуживания;
- что перед ручным запуском рекомендуется остановить контейнер/процесс 9Router, выполнить maintenance, затем запустить 9Router снова;
- что скрипт откажется работать, если не сможет взять `BEGIN IMMEDIATE` lock;
- как включить opt-in автозапуск через `ORR_AUTO_RUN_DB_MAINTENANCE=true`.

## Что НЕ менять

- Не запускать full `VACUUM` из фонового retention job'а.
- Не включать автозапуск по умолчанию.
- Не делать maintenance обязательным для старта приложения.
- Не поддерживать full VACUUM для `sql.js` в этой задаче.

## Критерии готовности

- `npm run db:enable-incremental-vacuum` существует.
- Скрипт отказывается запускаться при недостатке свободного места.
- Скрипт отказывается запускаться на `sql.js`.
- Повторный ручной запуск без `--force` не делает full `VACUUM`, если `_meta.autoVacuumMode=incremental`.
- Скрипт проверяет write lock через `BEGIN IMMEDIATE` / `ROLLBACK` и отказывается работать при busy database.
- Во время долгого `VACUUM` есть heartbeat-логирование.
- После успешного запуска `_meta` содержит `autoVacuumMode=incremental` и `autoVacuumMigratedAt`.
- `ORR_AUTO_RUN_DB_MAINTENANCE=true` запускает maintenance opt-in и не запускает его повторно после успешной миграции.
- Runbook содержит инструкцию оператора.
- Сборка 9Router проходит стандартной командой проекта или в отчёте указана причина, почему она не запускалась.

**Остаточные риски / Notes:**

- В compose-командной обёртке используется `sh -lc "...exec node /app/app/server.js"` — это не меняет `process.cwd()`, остаётся `/app`. Значит `process.cwd() + "/scripts/..."` резолвится правильно. Если кто-то меняет compose `command:` и добавляет `cd /app/app` перед `exec`, путь перестанет работать — это документировано комментарием в `initializeApp.js`.
- `docker compose run --rm 9router node ...`: первый `node` — аргумент для entrypoint (`exec su-exec node "$@"`), второй `node` — собственно вызов node. Выглядит избыточно, но корректно — su-exec интерпретирует `node` как user, остаток — как команду.
- Скрипт намеренно не пытается работать через `sql.js` (постановка задачи запрещает) — выходит с понятной ошибкой, если `better-sqlite3` недоступен.
- В дев-режиме старый сценарий `npm run db:enable-incremental-vacuum` тоже остаётся рабочим (скрипт self-contained, `node` найдёт `better-sqlite3` в `node_modules/`).
