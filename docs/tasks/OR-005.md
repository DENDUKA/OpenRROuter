## Что нужно сделать

### 1. Добавить Gateway-owned persistent store

Создать migration `db/migrations/gateway/001_usage_outbox.sql` со схемой `gateway`.

Минимальная таблица:

```sql
create table if not exists gateway.usage_outbox (
    request_id varchar(128) primary key,
    payload_json text not null,
    status varchar(32) not null,
    attempts integer not null,
    next_attempt_at_utc timestamptz not null,
    locked_by varchar(128) null,
    locked_until_utc timestamptz null,
    last_error text null,
    created_at_utc timestamptz not null,
    updated_at_utc timestamptz not null
);

create index if not exists ix_gateway_usage_outbox_due
    on gateway.usage_outbox (status, next_attempt_at_utc);
```

Использовать `request_id` как idempotency key. BillingService уже хранит `billing.usage_records.request_id` как primary key в `db/migrations/billing/001_initial.sql`, поэтому повторная доставка не должна создавать double-accounting. Не менять BillingService schema в рамках этой задачи.

### 2. Добавить репозиторий outbox

Создать `IUsageOutboxRepository` с операциями:

- enqueue usage event idempotently;
- lease/due batch for worker;
- mark delivered;
- mark failed with retry metadata.

Для Dapper/Postgres реализации lease должен быть конкурентно-безопасным. Использовать транзакцию и паттерн:

```sql
select request_id
from gateway.usage_outbox
where status = 'pending'
  and next_attempt_at_utc <= now()
order by next_attempt_at_utc
limit @batchSize
for update skip locked
```

Затем в той же транзакции пометить выбранные записи как leased/in-progress (`status`, `locked_by`, `locked_until_utc`, `updated_at_utc`). Наивный `SELECT` без `FOR UPDATE SKIP LOCKED` не допускается.

Для dev/test без connection string добавить in-memory реализацию, но явно отметить в коде/логах, что она не durable.

Если `ConnectionStrings:GatewayDb` задан, использовать Dapper/Npgsql repository по паттернам других сервисов.

### 3. Убрать fire-and-forget из request path

В `Startup.cs` заменить:

```csharp
_ = billingClient.RecordUsageAsync(usageEvent, CancellationToken.None);
```

на запись в outbox:

```csharp
await usageOutbox.EnqueueAsync(usageEvent, context.RequestAborted);
```

Ответ клиенту не должен ждать доставки в BillingService, только durable enqueue.

Для текущего buffered `/v1/chat/completions` flow ответ клиенту в коде пишется после получения ответа от 9Router и после извлечения usage. Поэтому порядок должен быть:

1. получить ответ от 9Router;
2. извлечь usage;
3. если `usage.InputTokens == 0 && usage.OutputTokens == 0` — **пропустить enqueue** и сразу отдать ответ клиенту, как в текущем коде на [Startup.cs:120](../../src/OpenRussiaRouter.ApiGateway/Infrastructure/Startup/Startup.cs#L120). Гард по нулевому usage сохраняется — нет события для учёта, нет блокировки клиента;
4. если usage > 0 — durable-enqueue usage event;
5. только после успешного enqueue записать upstream response клиенту.

Если durable enqueue в configured persistent GatewayDb недоступен в production, вернуть 500 и не отдавать upstream body клиенту. Это неприятно для клиента, но сохраняет инвариант: успешный billed response не теряется для биллинга.

Для dev in-memory режима enqueue best-effort, но это не production durable mode.

**Сознательное изменение SLA Gateway.** Эта схема делает GatewayDb обязательной зависимостью для публичного API. Сейчас при недоступности GatewayDb (fire-and-forget) запросы продолжают обслуживаться с потерей usage-событий; после внедрения этого outbox — при недоступности GatewayDb запросы отказываются с 500. Это сознательный архитектурный выбор в пользу billing-консистентности (миссия Gateway — корректный учёт оплачиваемых вызовов, а не максимальная availability любой ценой). Следствия для эксплуатации:

- мониторинг здоровья GatewayDb на уровне prod-инстанса Gateway — обязателен и должен быть на той же дежурной странице, что и сам Gateway;
- GatewayDb должен жить на той же VM/в том же VPC, что и Gateway — кросс-региональный Postgres недопустим;
- в runbook эксплуатации Gateway отметить новое поведение «GatewayDb down ⇒ API down».

Если в будущем будет реализован настоящий streaming endpoint, это потребует отдельной задачи: streaming нельзя безопасно закрыть тем же порядком после отправки токенов клиенту. Для streaming нужен pre-created outbox record до начала stream и последующее update with tokens/status после завершения stream, либо отдельный durable fallback.

Не реализовывать streaming outbox protocol в этой задаче.

### 4. Добавить worker доставки

Создать `UsageOutboxWorker` как hosted service:

- периодически выбирает due события;
- вызывает `IBillingGatewayClient.RecordUsageAsync`;
- при success/accepted помечает delivered или удаляет строку;
- при ошибке увеличивает attempts и ставит `next_attempt_at_utc` по backoff;
- после `MaxAttempts` переводит запись в `dead`;
- логирует request id, attempts и next attempt.

Конфиг:

- `UsageOutbox:Enabled` default `true`;
- `UsageOutbox:BatchSize` default `50`;
- `UsageOutbox:PollIntervalSeconds` default `5`;
- `UsageOutbox:BaseBackoffSeconds` default `2`;
- `UsageOutbox:MaxBackoffSeconds` default `300`.
- `UsageOutbox:MaxAttempts` default `20`.

Backoff: экспоненциальный `min(2^attempts * BaseBackoffSeconds, MaxBackoffSeconds)` с jitter ±20%. После `MaxAttempts` запись получает `status='dead'`, `last_error` сохраняет последнюю ошибку, worker больше не пытается доставлять её автоматически.

### 5. Зарегистрировать зависимости

В `ApiGatewayExtensions` зарегистрировать:

- connection factory, если задан `ConnectionStrings:GatewayDb`;
- Dapper repository или in-memory fallback;
- hosted worker.

Не ломать текущий режим запуска без Postgres для unit tests и локального dev.

## Критерии готовности

- В `Startup.cs` больше нет fire-and-forget `RecordUsageAsync`.
- Usage event сначала durable-enqueue'ится на стороне Gateway.
- Гард `usage.InputTokens == 0 && usage.OutputTokens == 0` сохранён: при нулевом usage enqueue пропускается, ответ клиенту отдаётся без блокировки.
- Изменение SLA Gateway (GatewayDb становится обязательной зависимостью публичного API) явно зафиксировано в runbook эксплуатации Gateway и в комментарии в `Startup.cs` рядом с новым enqueue-вызовом.
- Worker доставляет outbox-события в `BillingService.RecordUsage` с retry/backoff.
- Lease due batch использует Postgres row locking (`FOR UPDATE SKIP LOCKED`) или эквивалент, чтобы несколько Gateway worker'ов не брали один batch одновременно.
- После `UsageOutbox:MaxAttempts` запись переводится в `dead`.
- Повторная доставка одного `request_id` не приводит к double-accounting.
- Gateway сохраняет возможность запускаться в dev/test без GatewayDb через in-memory fallback.
- Добавлена миграция `db/migrations/gateway/001_usage_outbox.sql`.
- Добавлены тесты worker/repository/request flow.
