# Task Creator

Каталог `docs/tasks/` содержит задачи формата `OR-XXX.md`. Цель этого документа — формат, по которому любая ИИ-модель сможет выполнить задачу без догадок.

## Принципы

- Одна задача = одна завершённая цель. Не смешивать несвязанные изменения.
- Формулировать так, чтобы по тексту был понятен конечный результат.
- Язык — русский (как и соседние задачи).
- Никаких расплывчатых «улучшить», «починить», «привести в порядок» без конкретики.
- Писать как для исполнителя без доступа к контексту автора.

## Заголовок

`# OR-0XX: Краткое описание` — номер уникальный, описание отражает результат.

## Структура файла

1. Заголовок
2. `Complexity`
3. `Model` (название модели автора задачи или `unknown`)
4. `Dependencies`
5. `## Prompt`
6. `## Файлы`
7. `## Что нужно сделать`
8. `## Что НЕ менять` (опционально)
9. `## Критерии готовности`
10. `---`
11. `## Agent Report` (заполняется executor-ом)
12. `## Reviewer Report` (заполняется reviewer-ом)

Пустые блоки `Agent Report` / `Reviewer Report` оставлять как есть — структура должна сохраняться.

## Поля

### Complexity (1/10 … 10/10)

Оценивать по **худшему** из четырёх измерений:

- **Рассуждение** — нетривиальность логики, дизайна, edge-cases.
- **Объём контекста** — сколько файлов/строк нужно держать в голове одновременно.
- **Следование инструкциям** — сколько точных шагов, насколько важна дисциплина.
- **Риск галлюцинаций** — насколько критично не выдумывать API, сигнатуры, имена, пути.

Ориентиры:

- `1–2` — правка одной строки в известном файле.
- `3–4` — 2–3 файла, понятная логика.
- `5–6` — несколько слоёв, средний контекст.
- `7–8` — архитектурные решения или много edge-cases.
- `9–10` — системный рефакторинг, критичная логика.

Простая правка в 50 связанных файлах — это не `2/10`. Сложность ≠ важность.

### Model

См. `task-shared-policies.md` → раздел «Поле Model».

### Dependencies

Список задач-предшественников или `Нет`.

### Prompt

Короткое описание цели — зачем задача и какой ожидается результат.

### Файлы

- Только реально затронутые файлы.
- Пути относительные от корня репозитория.
- Действие у каждого: `(изменить)` / `(создать)` / `(удалить)`.
- Группировать по смыслу, если задача затрагивает несколько слоёв.

### Что нужно сделать

- Пронумерованные шаги, каждый проверяемый.
- Кодовые фрагменты — прямо в задаче, если они уточняют ожидаемое поведение.
- Важные ограничения — явно в этом разделе.

### Что НЕ менять (опционально)

Использовать, когда есть реальный риск scope creep:

- Файлы, которые задача не должна трогать.
- Архитектурные решения, которые нельзя «упрощать по пути».
- Публичные контракты/API, которые должны остаться неизменными.

### Критерии готовности

- Проверяемые результаты, не пожелания.
- Отвечают на вопрос: «как понять, что задача сделана?».
- Для кодовых задач — указывать, что должно пройти сборка/тесты.

## Спецификации по типам задач

- **API** — конкретные маршруты, методы, ожидаемые статусы.
- **UI** — поведение и сценарии проверки.
- **Конфиг** — точные ключи и значения.
- **Безопасность** — ограничения и способы проверки.
- **Логирование** — точные сообщения или формат.

## Шаблон

```md
# OR-0XX: Короткое название

Complexity: 3/10
Model: <модель автора или unknown>
Dependencies: OR-0YY

## Prompt

Кратко описать цель.

## Файлы

- `path/to/file` (изменить)
- `path/to/new-file` (создать)

## Что нужно сделать

### 1. Первый шаг

Что должно быть сделано.

### 2. Второй шаг

Что должно быть сделано.

## Что НЕ менять

- Контракт публичного API.

## Критерии готовности

- Проверяемый результат 1
- Проверяемый результат 2

---

## Agent Report

## Reviewer Report
```
