# Shared Policies (executor + reviewer)

Этот файл — единый источник правил для исполнителя и ревьюера. Если правило здесь, оно действует **и для executor, и для reviewer**. Не дублировать его в других prompt-файлах.

## Чувствительные участки

Эти категории трогать **только если это явно указано в задаче**. Если задача косвенно требует изменений в них, но прямо не просит — `Status=Blocked` и эскалация.

- **Криптография** — алгоритмы шифрования/хеширования, генерация токенов, соли, pepper, key derivation.
- **Идентификация и аутентификация** — формат хранения user ID, паролей, сессий, access tokens.
- **Синхронизация и целостность** — locks, outbox, очереди, транзакционные границы, идемпотентность, retry-логика.
- **Долгоживущие идентификаторы** — subscription tokens, API keys, публичные ссылки. Не регенерировать для существующих записей.
- **Retry/fallback механизмы** — не упрощать до прямых вызовов ради «чистоты кода». Они нужны такими, какие есть.

Если executor видит баг в этой зоне — фиксирует в `Notes`, **не исправляет** в рамках текущей задачи.
Если reviewer видит, что executor самовольно зашёл сюда — это `Changes Requested` или откат правки, не `Approved`.

## Схема данных и миграции

- Автогенерация миграций (любой ORM) — **только если явно в задаче**.
- Изменение entity / модели данных — отдельная строка в отчёте: `Migration required: Yes/No/N/A`.
- `DROP COLUMN` или переименование колонки в миграции = `Status=Blocked`, эскалация.
- Уже применённые в прод миграции **не редактировать**, только новые поверх.
- Автогенерированные миграции читать глазами (особенно SQLite — нет `ALTER COLUMN`).

Reviewer обязан проверить: если entity-классы изменились, но `Migration required: No` — переподтвердить, что миграция действительно не нужна.

## Сборка и тесты

- Использовать стандартные команды проекта. Если есть инструкция в `CLAUDE.md` / `AGENTS.md` / `README` — следовать ей.
- Допускается частичный прогон (конкретный проект, класс, фильтр), если этого достаточно по контексту задачи.
- В отчёте указывать **фактическую** команду или явную причину, почему тесты не запускались.

## Поле Model

- Если знаешь свою модель и версию — указывай (например, `Claude Sonnet 4.6`, `GPT-5.1`, `Gemini 3 Pro`).
- Если **не знаешь** — спроси у пользователя **сразу при получении задачи, до начала работы**. Не откладывай вопрос на конец: пользователь, скорее всего, рядом в момент постановки и сможет ответить за секунды; в конце выполнения он может быть уже не у компьютера, и задача зависнет.
- Формулировка вопроса короткая: «Не знаю свою модель — назови её, чтобы заполнить поле Model в отчёте».
- Если пользователь не отвечает или явно говорит «не важно» — `unknown`, продолжаем работу.

Поле обязательное в `Agent Report` и `Reviewer Report` — оно используется для накопления статистики «какая модель справляется с какой спецификой задач».

## Общие требования

- Отчёты — на русском, кратко и предметно.
- Пути к файлам — относительные от корня репозитория.
- Не удалять исходный текст задачи и не переписывать её формулировку.
- Не удалять предыдущие отчёты — добавлять свой **в самый низ** task-файла.
